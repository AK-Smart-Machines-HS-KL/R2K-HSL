# Changelog Archival Protocol (v1)

## Purpose

Keep `SESSION_CHANGELOG.md` at a manageable size. When triggered (size guard
fires at >100 KB), move older entries to `SESSION_CHANGELOG_archive.md` so the
active file contains only operationally relevant recent sessions. Findings from
archived entries must be distilled to power files first — the changelog is a
log, not a knowledge base.

## Trigger

The `session_entry.sh` size guard warns when the active changelog exceeds
**100 KB**. Archival should happen within the next 1-2 sessions. If the guard
isn't installed yet (e.g., first archival post-adoption), use judgment: any
file >80 KB with entries older than 2 weeks is a good candidate.

## Prerequisites

- The active changelog has a recent session entry (the guard warned during or
  after this session).
- No concurrent benchmark or experiment that would append entries mid-run.
- You know the cutoff date (entries >= this date stay active). Default: entries
  before **2026-08-23** get archived.

## Procedure

### Phase 0 — Pre-flight
1. Confirm no benchmark is running (`ps aux | grep benchmark | grep -v grep`).
2. Read the last changelog entry to know the current session state.
3. Note the active file's byte + line count:
   ```bash
   wc -c -l docs/SESSION_CHANGELOG.md
   ```

### Phase 1 — Distillation-debt sweep

Every entry being archived must have its findings reflected in the RAG power
files. For each entry heading the archive boundary, grep the entry for "Not yet
done" items that promise KB updates (e.g., "KB updates to 8_C3_SOCCER_KNOWLEDGE.md").
Verify each promise:

```bash
grep -n "AKM\|n=200\|goalie 0 passes\|<keyword>" src/ros2k_knowledge/8_C3_SOCCER_KNOWLEDGE.md
grep -n "<keyword>" src/ros2k_knowledge/META_KNOWLEDGE_ROUTER.md
```

If a promise is unpaid, either:
- **Pay it:** add the finding to the appropriate power file, then archive the
  entry cleanly (findings survive in the KB).
- **Defer:** keep the entry in the active file until the next archival cycle.


### Phase 3 — The move (entry-granular, not raw line ranges)

1. **Extract to-archive entries** by scanning for `^## 2026-` headers, selecting
   those with date < cutoff, and extracting their content (header to next header
   or end-of-file). A python script can do this deterministically.

2. **Re-sort archived block** chronological (oldest-first, base before cont.N).
   Append to `SESSION_CHANGELOG_archive.md` — the archive's existing 30 entries
   (2026-07-13 → 2026-08-02) already follow oldest-first.

3. **Rebuild active file:**
   - Update header note to: `> For full history (2026-07-13 to 2026-08-22), see
     SESSION_CHANGELOG_archive.md. Compressed on 2026-08-26.`
   - Keep entries >= cutoff, in strict newest-first order (move any
     bottom-appended entries up to the top section).
   - Drop the `<!-- Stub generated by ... -->` and `<!-- Last commits: ... -->`
     comments from the archived entries (they're noise in the archive). Keep
     the `---` separators between entries for readability.

4. **Update archive trailing note** to:
   `Active changelog contains entries from 2026-08-23 onward.`

### Phase 4 — Verification

```bash
# Entry count: kept + archived should equal original
grep -c "^## 2026" docs/SESSION_CHANGELOG.md
grep -c "^## 2026" docs/SESSION_CHANGELOG_archive.md
# Original was N entries; now should be K kept + N-K archived

# Byte total roughly conserved (± header edits)
wc -c docs/SESSION_CHANGELOG.md docs/SESSION_CHANGELOG_archive.md

# git diff review — only moves, no content loss
git diff --stat
git diff docs/SESSION_CHANGELOG.md      # should show deletions-only (no added content)
git diff docs/SESSION_CHANGELOG_archive.md  # should show additions-only (no deleted content)
```

If the archive is already tracked in git (it is), moving content between tracked
files produces a clean diff: deletions in one, additions in the other. No file
is actually deleted.

### Phase 5 — Session protocol + commit

1. Append the archival session entry to the changelog (session_entry.sh stub +
   narrative). This entry lands in the KEEP set by date.
2. Commit the docs changes:
   ```bash
   git add docs/CHANGELOG_ARCHIVAL.md docs/SESSION_CHANGELOG.md docs/SESSION_CHANGELOG_archive.md
   git commit -m "docs: archive changelog pre-2026-08-23, document archival protocol"
   git push
   ```

## Growth-prevention mechanisms (apply during this session)

These ensure the archival is the last "emergency" one — future size is
self-regulating.

### M1 — Tail-read protocol (AGENTS.md, line 13)

Change the changelog reading instruction from "READ THIS FIRST" (whole file) to
a tail-first approach:

```diff
-- `core/docs/SESSION_CHANGELOG.md` — **READ THIS FIRST after a reboot.** Append-only session log: what was done, what's next, what's blocking. Cross-session continuity.
+- `core/docs/SESSION_CHANGELOG.md` — **READ THE LAST ~150 LINES FIRST after a reboot.** Append-only session log: what was done, what's next, what's blocking. Cross-session continuity. Grep the full log + archive for deeper history.
```

### M2 — Size guard (session_entry.sh, after line 87)

Add to the end of `session_entry.sh`:

```bash
# Size guard — warn if changelog exceeds threshold
CHANGELOG_FILE="docs/SESSION_CHANGELOG.md"
if [ -f "$CHANGELOG_FILE" ]; then
    SIZE_BYTES=$(wc -c < "$CHANGELOG_FILE")
    THRESHOLD=$((100 * 1024))
    if [ "$SIZE_BYTES" -gt "$THRESHOLD" ]; then
        SIZE_KB=$((SIZE_BYTES / 1024))
        echo "" >&2
        echo "============================================================" >&2
        echo "  CHANGELOG SIZE GUARD: $SIZE_KB KB > 100 KB threshold" >&2
        echo "  Run the archival protocol: docs/CHANGELOG_ARCHIVAL.md" >&2
        echo "============================================================" >&2
    fi
fi
```

Uses stdout for the guard message (it's informational, not part of the stub).
The `>&2` is optional — session_entry.sh already outputs to stdout for pasting.

### M3 — Entry discipline (implicit, no code change)

Keep entries concise (~40 lines max). Findings, tables, and detailed results
belong in `src/results/*.md` or power files; the changelog entry links them.
The 7 required sections (goal/done/files/deleted/not-done/next/blockers) fit
in ~30 lines with bullet links instead of inlined analysis.
