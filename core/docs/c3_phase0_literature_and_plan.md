## 1. Literature surveyed

### 1.1 Model switch: qwen2.5-coder:3b → qwen2.5:3b

**Investigated:** Qwen2.5-Coder Technical Report (Hui et al. 2024, arxiv 2409.12186).
The training corpus (`Qwen2.5-Coder-Data`, 5.5 trillion tokens) is **proprietary and not released**. The report describes its composition:

| Data type | Source | Proportion | Soccer vocabulary? |
|---|---|---|---|
| Source Code | GitHub public repos (pre-Feb 2024), 92 languages. PRs, commits, Jupyter, Kaggle. | 70% of final mix | No |
| Text-Code Grounding | Common Crawl (code docs, tutorials, blogs). 4-stage fastText filtering. | Part of 20% Text | Minimal — code-focused text only |
| Synthetic Data | Generated by CodeQwen1.5, validated with executor (only executable code retained). | Part of 70% Code | No |
| Math Data | From Qwen2.5-Math pretraining corpus. | 10% of final mix | No |
| Text Data | High-quality general NL from Qwen2.5 corpus. **Code segments stripped out.** | Part of 20% Text | Possible — this is the only component with general text exposure |

**Final mixture:** 70% Code, 20% Text, 10% Math. The 70:20:10 ratio outperformed 100:0:0 and 85:15:5 — Math and Text positively contribute to code performance once they reach a threshold.

**Conclusion:** Qwen2.5-Coder is a code-specific model. Its "Text Data" component (general NL, code-stripped) is a small fraction of total training. Soccer commentary, coaching texts, and game analysis are almost certainly NOT well-represented. The base Qwen2.5 (non-coder) has broader web/book/multilingual text exposure where sports vocabulary lives.

**Decision:** Switch from `qwen2.5-coder:3b` to `qwen2.5:3b` (Qwen2.5-3B-Instruct) for all C3 work. The Coder variant's training distribution is wrong for soccer vocabulary probing.

**Post-training (§4 of the report):** Instruction data synthesized from GitHub code snippets via LLM, multilingual multi-agent collaborative framework, checklist-based scoring (9 quality dimensions), multilingual sandbox for code verification, DPO with code execution feedback. All code-focused — no general instruction-following data relevant to soccer.

**Architecture continuity:** `qwen2.5:3b` shares the same architecture (Qwen2.5, 36 layers, GQA 16/2 heads, 151,646 vocab, 32K context). The evaluator, bridge, trace logging, dynamic prompt injection, and content-hash skip are all architecture-level — they work identically with either variant. Only the model weights differ.

**C-series baselines invalidated:** The 11.8% win rate (C1+C9) was measured with the Coder model. A new baseline with `qwen2.5:3b` is needed. It runs as a background Gazebo task parallel to Phase 1 (vocabulary probing is interactive, doesn't need the GPU for continuous inference).

**Regression test with Llama-3.2-3B (later phase):** After the inter-lingua is validated with Qwen2.5-3B on Gazebo (Phase 4), run the Phase F winning config with `llama3.2:3b` as a text-probe regression test. This tests whether the inter-lingua is model-agnostic (works across families) or Qwen-specific. Llama 3.2 is also the candidate for Phase 5 edge deployment (Jetson AGX/Orin for K1 onboard compute).

### Intent-based control / controlled vocabulary

| Paper | arXiv | Inter-lingua form | Lesson for our controlled vocabulary |
|---|---|---|---|
| **SayCan** (Ahn 2022) | 2204.01691 | Natural-language *action labels* ("go to the counter", "pick up the can"). NOT JSON. An *affordance function* (value head) scores each label for feasibility. | Their LLM outputs natural-language action labels — exactly our controlled vocabulary. The "affordance" = feasibility check is separate. In ROS2K, the *bridge* is the implicit affordance function (it executes whatever it can parse). SayCan validates: constrain the output to a known label vocabulary, let a separate layer handle feasibility. |
| **RoboMatrix** (Mao 2024) | 2412.00171 | Skill API: named skills with typed params. "Skill" = verb + args. Output is structured but human-readable. | Their "skill" = our "verb+noun+adjective sequence." | **BTGenBot-2** (Izzo 2026) | 2602.01870 | 1B model generates XML behavior trees from NL + a *list of action primitives* (the controlled vocabulary is *given* to the model). 90% zero-shot, beats GPT-5. | **Most actionable finding.** A 1B model outperforms GPT-5 when (a) the output vocabulary is small and pre-specified, (b) the model is given the primitive list as input. | **EmboTeam** (Zeng 2026) | 2601.11063 | LLM → PDDL → classical planner → BT. PDDL is the inter-lingua. 12%→55% success. | PDDL is too heavy for soccer (no long-horizon symbolic goals). | **SCOPE** (Hindsbo 2026) | 2606.02951 | Qwen3 SLMs for natural-language PTZ camera control. Tool routing (call the right tool from NL). Their finding: once the SLM is capable enough, *perception* is the bottleneck, not planning. For us: once the vocabulary is right, the *world model* (perception) becomes the bottleneck → connects to "world models not overkill long-term." |

### Watchdog / runtime verification

| Paper | arXiv | Key finding | ROS2K relevance |
|---|---|---|---|
| **Correlation matrix rank self-verifier** (Liu 2025) | 2510.24299 | The LLM checks its *own* output correctness via internal correlation-matrix rank — no separate model needed. 75% accuracy in distinguishing correct from incorrect reasoning paths. | Relevant to watchdog Option A. Instead of a second model, the *same* 3B model's internal activations can signal "I'm unsure." Cheap, no extra latency. But: needs access to internal activations (logits/hidden states), which Ollama's REST API doesn't expose. Would need a direct `transformers` call instead. |
| **LLMs gaming verifiers** (Helff 2026) | 2604.15149 | RLVR-trained models learn to *game* verifiers — produce outputs that pass the check without being correct. "Imperfect verifiers admit false positives." | Warning for watchdog Option B. A second 3B model as monitor would be an imperfect verifier. The 3B model might learn to produce outputs that pass the monitor but are still wrong. Mitigated by: (a) monitor checks *world-state consistency* (did the bot reach the target?), not *output quality* — harder to game. |
| **Orchestration gap** (Galanti 2026) | 2607.21725 | Separating reasoning from execution gives 4× improvement (12.8%→53.3%). Orchestrator does outcome tracking + failure recovery. | **The watchdog IS the orchestrator.** It tracks outcomes (predicted vs actual) and triggers recovery. The Galanti paper says this is where the 4× gain comes from — not from a bigger LLM, but from *closing the loop*. |

### Interwoven few-shot / prompt structure

**No paper found** on "interwoven rules+examples" vs "separate rules+examples" specifically. The literature on in-context learning focuses on *what* examples to choose, not *how to structure* them relative to global instructions. This is a gap our Phase F fills.

Closest findings:
- **BTGenBot-2:** gives the model a *list of action primitives* (the rules) *and* few-shot examples. They're separate. 90% on 1B. Suggests separate is fine for structured output (XML BTs).
- **SayCan:** gives the model *only* action labels (no examples). The affordance function does the grounding. Suggests: if the vocabulary is small enough, you don't need examples at all.
- **The "pattern copier" finding** (from C-series): the 3B model copies the *strongest signal* in the prompt. If rules are separate and dominant, the model copies rules (format, not content). If examples are dominant, the model copies examples. If they're *interwoven*, the model copies the *integrated pattern* (rule+example together).

**Hypothesis for the interwoven extreme:** If we embed rules *inside* the examples (e.g. a sample that says "blue_2 chase the ball — rule: striker always chases"), the model sees the rule *in context* of an action, not as an abstract global instruction. This might improve rule-following because the 3B model learns "when I see this situation, I apply this rule" rather than "memorize this rule list." This is untested — no prior work.

## 2. Key takeaways for C3

1. **Controlled vocabulary = constrain the output space, not the output format.** SayCan, RoboMatrix, and BTGenBot-2 all keep the output as natural language (or XML) but restrict it to a *known vocabulary of verbs/labels*. The 3B model doesn't invent new actions — it *selects and parameterizes* from a list. Phase 1's job is to discover which verbs/nouns Qwen 3B *already* knows, so we can give them back to it as the allowed vocabulary. BTGenBot-2 proves a 1B model can do this at 90% accuracy.

2. **No rule-based mapper = no verifier (without watchdog).** EmboTeam and the orchestration-gap paper both add a *correctness check* between the LLM and execution. Without a mapper, LLM errors propagate directly to the bridge. The watchdog (Phase W) closes this gap — it's not optional infrastructure, it's the *orchestrator* that Galanti says gives 4× improvement.

3. **Composite score as diagnostic, not metric.** The composite decomposes win rate into: goal_diff (0.4), tactical_score (0.3), possession (0.2), latency (0.1). If win rate is flat but possession rises, you know the next lever is goal conversion. It tells you *what* broke or improved, not *whether* you won.

4. **World models are long-term, not overkill.** SayCan's affordance bottleneck, SCOPE's "perception becomes the bottleneck once SLM is good enough," and our C9 finding converge: prediction doesn't help the *LLM input*, but it helps *failure detection* (predicted vs actual divergence). Once on real hardware (non-deterministic physics), a learned world model becomes necessary. Keep Phase 5.1 on the roadmap.

5. **LLCoach validates the LLM-coach architecture for RoboCup.** A large LLM generating soccer plans that beat human-coded bots is proven. The open question: can a *3B* model do it at *tick-level* (~750ms) granularity? The answer from C-series (11.8% win rate) is "barely." The inter-lingua aims to close the gap by making the 3B's job *selection* (easy for small models) rather than *generation* (hard for small models).

6. **The "continue" token is a latency optimization, not a reasoning feature.** No paper found on LLMs outputting a skip-token. Our content-hash skip already saves 64% at the system level. A model-level "continue" saves the remaining 36% but risks the model defaulting to "continue" when it should act. Defer to Phase 1 experiment 3, low priority.

7. **Interwoven few-shot is untested territory.** No prior work on embedding rules inside examples vs keeping them separate. The "pattern copier" finding suggests interwoven might work better (the model copies the integrated rule→action pattern). Phase F tests this.

8. **Model choice matters for vocabulary.** Qwen2.5-Coder's training data is 70% source code, 20% text-code grounding, 10% math (arxiv 2409.12186). Soccer vocabulary is not in-distribution for a code-specific model. Switched to Qwen2.5-3B-Instruct (general-purpose) which has broader web/book/multilingual text exposure. The model switch invalidates C-series Gazebo baselines — a new baseline runs parallel to Phase 1.

9. **Llama-3.2-3B as regression test and edge candidate.** Phase 4b tests whether the inter-lingua is model-agnostic (works across Qwen/Llama families) or Qwen-specific. Llama 3.2 is also the candidate for Phase 5 edge deployment (Jetson AGX/Orin for K1 onboard compute).

## 4. The text-only iteration loop (shared by Phases 1, F, 3, W)

```
1. Craft or select synthetic world-state JSON (game situation)
2. Assemble prompt (from fragments / interwoven samples)
3. POST to Ollama (qwen2.5:3b — switched from coder, see §1.1)
   - --no-explain mode: ~700ms per probe (est., verify on first probe)
   - --explain mode: ~1100ms per probe (est., verify on first probe)
4. Analyze the text output:
   - Does it use controlled vocabulary? (valid verb+noun+adjective sequences)
   - Does it follow rules? (no OOB targets, no contradictive argumentation)
   - Are assignments valid JSON? (parseable, all bots assigned)
   - Does analysis/oracle contain useful text or hallucinated JSON?
   - Does it output "continue" when appropriate?
5. Iterate on prompt structure / vocabulary / sample design
6. Repeat (hundreds of probes in minutes, not hours)
```

**Synthetic world data sources:**
- **Existing trace data:** 27 baseline runs in `logs/world_trace_*.jsonl` — extract real game frames at key moments (kickoff, ball-out, attack, defense, set-pieces). Thousands of real situations, already in the right JSON format.
- **Hand-crafted situations:** Specific edge cases the traces don't cover (bot clustered, ball in own goal area, 2vs1 overload, referee restart states).
- **Procedural variations:** Take a real frame, perturb positions (move ball ±1m, swap red positions) to generate controlled variations.

**Why this is dramatically faster:**
- 1 Gazebo match = 120s + ~30s container restart = ~150s per data point
- 1 LLM probe = ~700ms (no-explain) or ~1100ms (explain) per data point (est. for qwen2.5:3b)
- Speedup: ~135× (no-explain) or ~85× (explain)
- 100 probes = ~1.5 min (no-explain) or ~2 min (explain)
- 100 Gazebo runs = ~4 hours

### Phase 1: Vocabulary probing — DONE (56 probes, 2026-08-01)

**Goal:** Discover Qwen2.5-3B-Instruct's soccer vocabulary through direct conversation. Create a controlled vocabulary of verb+noun+adjective sequences.

**Model:** `qwen2.5:3b` (switched from `qwen2.5-coder:3b`, see §1.1). User must `ollama pull qwen2.5:3b` before starting.

**Method:** Interactive. You + GLM converse with Qwen 3B via Ollama API (curl or a simple script). No `llm_probe.py` yet — discovery is conversational.

**Key experiments:**
1. Ask Qwen to describe what a specific bot should do in a given game state. Keep responses that form valid instruction sequences (verb + target + qualifier). Discard isolated nouns — they're not instructions.
2. Probe for soccer-tactics vocabulary: "formation", "wing play", "zone-defend", "marking", "press", "clear", "receive pass", "support run". Which does Qwen know? Which does it use correctly in context?
3. Test "continue" token: present Qwen with an unchanged vs changed world state. Can it reliably output "continue" vs a new strategy? (Low priority — content-hash skip already saves 64%.)
4. Create the controlled vocabulary: a set of verb+noun+adjective *templates* with slots. E.g. `[bot] [verb] [target] at [qualifier]`. These become the basis for the new `samples_*.txt` content.

**Important:** The 3B model is a pattern copier. The vocabulary should match Qwen's training distribution. With the switch to the general (non-coder) model, sports commentary, coaching texts, and game analysis are now more likely in-distribution. Words like "formation," "wing play," "zone-defend" should be tested. Words like "phantom kick," "PID controller," "tmpfs" are NOT.

**Verify latency on first probe:** The estimates in §3 (~700ms no-explain, ~1100ms explain) are from the Coder variant. The general variant shares the same architecture but may differ slightly. Run a timing test on the first curl call and update §3 if needed.

### Phase I: Transform builder — DONE (text-only, committed 2026-08-01)

**Goal:** Replace the JSON `min_ents` world encoding in `r2k_evaluator.py` with a condensed text transform in dictionary vocabulary (~250 tok cap).

**Method:**
- Build transformed text from the world snapshot: positions (`blue_1 at (x, y)`), ball, score, status, velocity — rich fact tiers from `8_C3_SOCCER_KNOWLEDGE.md` patterns (P1–P10) where cheap
- Content-hash skip hashes the TRANSFORMED text (not the JSON)
- Output format locked: coords in text (`blue_1 move to (2.2, 0.3)`), one line per bot, regex parse + JSON-style fallback (extended `parse_code`)
- `num_predict` no-explain 150→~200 (text output is longer than JSON)
- Explain mode keeps `ANALYSIS:`/`ORACLE:`/bot-line sections, `num_predict` 600

**I3 battery (20 situations, qwen2.5:3b):** verify transform renders sensibly, fits token budget, latency impact vs JSON encoding.

**Results (final run, 2026-08-01):**

| Metric | JSON | TEXT |
|---|---|---|
| Parse OK | 20/20 | 20/20 |
| Full coverage (one line per bot) | 18/20 | 20/20 |
| Latency p50 | 928 ms | 443 ms (−52%) |
| User-prompt tokens | ~48 | ~90 |

**Key fixes found during the battery (3 iterations):**
1. **Example-copy bug:** with literal example coords in the format spec (`move to (2.2, 0.3)`), the model echoed them verbatim regardless of the world. Fix: `X, Y` placeholders + "Do NOT copy example coordinates" law.
2. **Coverage bug:** model emitted only 1 line (or repeated the same bot). Fix: explicit "ONE LINE PER BOT — never use the same bot twice" law + "Command: blue_1, blue_2, blue_3" enumeration line in the user payload.
3. **Restart singularity:** game-phase fragments describe only the restart bot; model dropped the other bots. Fix: "Output one line for every other blue bot too" appended to all 4 game-phase fragments.
4. **`hold position` verb added** (dictionary-usable): 4th valid output line, parsed to `{"action": "Hold"}`, bridge skips movement (new `action == 'hold'` branch).

**Deliverable:** transform implementation + battery results.

### Phase K: Behavior battery — NEXT (text-only, the decision phase)

**Goal:** The experiment that decides whether the inter-lingua works. Dual A/B of current JSON-in/JSON-out vs transformed-text-in/condensed-text-out.

**K1: Situation corpus** — 40–60 hand-crafted situations from `8_C3_SOCCER_KNOWLEDGE.md` patterns (P1–P10, P-D6a) + referee states (ball-out, goal-kick, corner-kick-in, kickoff) + edge cases.

**K2: Dual A/B (no-explain 2×2 first; explain axis deferred):**

| Output format → / Input encoding ↓ | JSON (current) | Transformed text |
|---|---|---|
| JSON output | current baseline | — |
| Condensed text output | — | candidate |

Judged by: `parse_success`, `vocab_compliance`, `rule_following`, `contradiction_score`, `role_coverage` + human review.

**K3: Selective rules + oracle evaluation** — pull rules from `8_C3_SOCCER_KNOWLEDGE.md` + 11 `analysis.md` files; per-gap rule-vs-example form test (RQ2 re-check — B-study "1-sample" finding doubted at n=3); oracle field kept and evaluated per decision.

### Phase F: Few-shot paradigm rework — NEW (after Phase K, text-only)

**Goal:** Find the prompt structure that makes the 3B model produce the best instruction sequences. No Gazebo — pure LLM text-output analysis with synthetic world data.

#### F1: Build the probe instrument

**Tool:** `tools/llm_probe.py`
- Input: a directory of synthetic world-state JSONs + a prompt config (which fragments to assemble)
- For each world-state: assembles the prompt (via the same `_assemble_prompt()` logic from `r2k_evaluator.py`), POSTs to Ollama, captures raw text output
- Supports both `--no-explain` (num_predict=150, ~700ms est.) and `--explain` (num_predict=600, ~1100ms est.) modes with `qwen2.5:3b`
- Output: `results/probe_<config>_<situation>.jsonl` — one record per probe: world-state, assembled prompt, raw LLM output, parsed assignments, analysis text, oracle text, latency, parse success
- Batch mode: run N probes across M situations with a given config, produce a summary

**Synthetic data set:** `tests/synthetic_worldstates/`
- Extract 50–100 representative frames from existing `world_trace` files (kickoff, attack, defense, ball-out, goal-kick, corner-kick-in, cluster, OOB-risk, 2vs1, 3vs2)
- Hand-craft 20–30 edge cases (referee restart states, ball exactly on sideline, all bots in one half, etc.)
- Total: ~100 synthetic world-states, covering the situation space

#### F2: Define text-analysis metrics

Instead of Gazebo KPIs, we measure **output quality** directly:

| Metric | What it measures | How computed |
|---|---|---|
| `parse_success` | Did the LLM produce valid JSON assignments? | `json.loads()` on extracted JSON |
| `vocab_compliance` | Does the output use controlled vocabulary? | Check action verbs against the allowed list from Phase 1 |
| `rule_following` | Does the output follow the rules in the prompt? | Heuristic checks: no OOB targets (x/y within field bounds), goalie stays near goal line, no contradictive analysis text |
| `analysis_quality` | Is the analysis text meaningful or hallucinated? | Check: not empty, not JSON blob, not verbatim copy of sample, contains soccer-relevant terms |
| `oracle_quality` | Is the oracle text a prediction or a parrot? | Same checks as analysis_quality |
| `contradiction_score` | Does analysis contain contradictive argumentation? | Keyword check: "but also near own goal", "while also defending", "prioritize X while also Y" |
| `role_coverage` | Are all N bots assigned? | Count assignments vs expected bot count |
| `continue_accuracy` | Does the model output "continue" when state is unchanged vs changed? | Compare output across identical vs perturbed states |
| `latency_ms` | LLM response time | From API call timing |

#### F3: Run the structure sweep

**Configs to test:**

| Config | Global rules | Global samples | Interwoven samples | What we're testing |
|---|---|---|---|---|
| **F0** (baseline) | `rules_core.txt` + `rules_3vs3.txt` | `samples_3vs3.txt` | None | Current architecture. Reference point. |
| **F1** | `rules_core.txt` (minimal) | None | `samples_interwoven_3vs3.txt` | Rules embedded inside each sample as inline commentary. |
| **F2** | None | None | `samples_interwoven_full_3vs3.txt` | **Extreme.** No global text. Each sample = state + analysis + rule + expert + assignments, all in one block. |
| **F3** | `rules_core.txt` only | None | `samples_interwoven_3vs3.txt` (with analysis+oracle inline) | Axioms stay global, everything else embedded. |

**What "interwoven" means concretely:**

Current sample (separate, F0):
```
EXAMPLE:
INPUT: {"ball": {"x": 0.5, "y": 0.2}, "blue_1": {"x": -1.0, "y": 0.0}, ...}
ASSISTANT: {"assignments": [{"bot": "blue_1", "action": "move", "target": [0.3, 0.2]}, ...]}
```

Interwoven sample (F1/F2):
```
EXAMPLE:
INPUT: {"ball": {"x": 0.5, "y": 0.2}, "blue_1": {"x": -1.0, "y": 0.0}, ...}
ANALYSIS: Ball is in our half, blue_1 is closest. Red_2 is pressing from the right.
RULE: The closest bot to the ball always chases. Other bots maintain formation.
EXPERT: Blue_1 should chase the ball toward the right wing. Blue_2 should cover the center.
ASSISTANT: {"assignments": [{"bot": "blue_1", "action": "move", "target": [0.3, 0.2]}, ...]}
```

**Procedure:**
1. For each config: assemble prompt, run 100 probes (one per synthetic world-state), 3 repetitions (to check variance at temp:0.0 — should be deterministic, but verify)
2. Compute the 9 text-analysis metrics for each config
3. Compare configs: which produces highest parse_success, vocab_compliance, rule_following? Which has lowest contradiction_score?

**Time estimate:**
- F0 (no-explain, separate samples): 300 probes × ~700ms = ~3.5 min
- F1–F3 (explain, interwoven with analysis+oracle): 900 probes × ~1100ms = ~16.5 min
- **Total F3: ~20 min** (no Gazebo, estimates — verify on first run)

#### F4: Sweep content amount

Within the winning structure from F3, sweep:

| Variable | Values | What we're testing |
|---|---|---|
| Sample count | 1, 3, 6 | B-study found 1 is best for *separate* samples. Does this hold for *interwoven*? |
| Roles mentioned | 3 (goalie/attacker/defender), 5 (old set), 0 (no explicit roles) | Does the 3B model do better with fewer roles or no roles at all? |
| Rule density | 1 rule/sample, 3 rules/sample, all rules in every sample | How much rule text can the 3B model absorb per sample before it degrades? |
| Analysis presence | With analysis, without analysis | Does the analysis field help or harm output quality? (ECoT says CoT is noise on 7B — verify on 3B) |
| Oracle presence | With oracle, without oracle | Does the oracle field help or is it just parroted? |

**Time estimate:**
- ~15 configs × 100 probes = 1500 probes
- Mixed no-explain / explain: ~10 min
- **Total F4: ~20 min** (no Gazebo)

#### F5: Qualitative deep-dive

For the top 2–3 configs from F4:
- Manually inspect 20 LLM outputs per config
- Categorize: "good instruction" (sensible soccer action), "bad instruction" (OOB, passive, contradictive), "parse failure" (invalid JSON)
- Look for *patterns*: does the model fail on specific situations? (e.g. always bad on ball-out, always good on attack)
- Compare to the controlled vocabulary from Phase 1 — does the model use the discovered vocabulary or revert to jargon?

**Deliverable:** Phase F report — which structure + content amount produces the best LLM text output, with metrics and qualitative examples. No Gazebo runs.

### Phase W: Watchdog & closed-loop feedback — NEW (parallel to Phase 2–3, text-only)

**Goal:** Design and text-test the watchdog. No Gazebo — synthetic world states + LLM output analysis.

#### W1: Define divergence detection

The watchdog detects when the *predicted* world state (from the last LLM call) diverges from the *actual* world state (at t+746ms). We test this with synthetic data.

**Synthetic divergence scenarios** (`tests/synthetic_divergence/`):
- **No divergence:** t and t+746ms states are the prediction result (ball moved as expected, bots moved as expected). Watchdog should say "OK."
- **Ball divergence:** ball was at (0.5, 0.2) moving toward (0.8, 0.2), but at t+746ms it's at (0.5, -1.0) — bounced or pushed. Watchdog should say "STALE."
- **Bot divergence:** blue_1 was instructed to move to (0.3, 0.2), but at t+746ms it's still at (-1.0, 0.0) — stuck or blocked. Watchdog should say "STALE."
- **Score divergence:** score was 0-0, now it's 0-1 — red scored unexpectedly. Watchdog should say "STALE."
- **Status divergence:** status was "playing", now it's "ball_out" — referee stopped play. Watchdog should say "STALE."
- **Noise:** positions jitter by ±0.05m (tracker noise). Watchdog should say "OK" (not trigger on noise).

#### W2: Test Option A — re-prompt the 3B model on divergence

**Mechanism:** When divergence is detected, re-prompt the 3B model with: "The situation changed unexpectedly. Previous instruction was X. Actual state is Y. What should the bots do now?"

**Text-analysis test (via `llm_probe.py`):**
1. Take a synthetic world-state, get the LLM's instruction (call 1, ~700ms no-explain or ~1100ms explain).
2. Generate a divergent t+746ms state (from W1 scenarios).
3. Re-prompt the LLM with the divergent state + previous instruction (call 2, ~1100ms explain).
4. Analyze call 2's output:
   - Does it produce a *different* instruction than call 1? (It should — the situation changed.)
   - Is the new instruction *sensible* for the new situation? (Heuristic check.)
   - Does it acknowledge the change in its analysis text? ("Ball was pushed to the sideline, adjusting...")
   - Latency: how much extra time does the re-prompt add?

**Metrics:**
| Metric | What it measures |
|---|---|
| `divergence_detection_rate` | % of divergent scenarios where the watchdog correctly triggers a re-prompt |
| `false_positive_rate` | % of no-divergence / noise scenarios where the watchdog incorrectly triggers |
| `re_prompt_sensibility` | Does the re-prompted instruction make sense for the new situation? (heuristic) |
| `re_prompt_latency_ms` | Extra latency from the re-prompt call (~1100ms expected) |
| `re_prompt_acknowledgment` | Does the analysis text acknowledge the situation change? |

**Time estimate:** 50 divergence scenarios × 2 calls × ~1100ms = ~2 min.

#### W3: Test Option B — second model as monitor

**Mechanism:** A second, faster model (e.g. `qwen2.5:1.5b` or `llama3.2:1b`) receives the last instruction + current state + predicted state, outputs "OK" or "STALE."

**Text-analysis test (via `llm_probe.py` with model override):**
1. Take the same synthetic divergence scenarios from W1.
2. Send to the monitor model: "Previous instruction: X. Predicted state: Y. Actual state: Z. Is the instruction still valid? Answer OK or STALE."
3. Analyze the monitor's output:
   - Does it output "OK" for no-divergence scenarios?
   - Does it output "STALE" for divergence scenarios?
   - Latency of the monitor call (1.5B model: ~300–400ms expected).
   - Does it work on the 1.5B model, or does it need the 3B?

**Metrics:**
| Metric | What it measures |
|---|---|
| `monitor_accuracy` | % correct OK/STALE judgments across all scenarios |
| `monitor_false_positive_rate` | % of OK scenarios judged STALE |
| `monitor_false_negative_rate` | % of STALE scenarios judged OK |
| `monitor_latency_ms` | Monitor model response time (~300–400ms for 1.5B) |
| `monitor_model_size` | 1.5B vs 3B — does the smaller model work? |

**Time estimate:** 50 scenarios × 1 call × ~400ms = ~20 sec per model. Test 2 models (1.5B + 3B) = ~40 sec.

**Risk:** Two Ollama instances compete for GPU VRAM. On a single-GPU machine, this may not be feasible. Test VRAM contention as part of W3.

#### W4: Compare and decide

Compare Option A (re-prompt the 3B) vs Option B (second model monitor):
- Accuracy: which detects divergence more reliably?
- Latency: which adds less overhead? (A: +1190ms on divergence only. B: +400ms every tick.)
- Simplicity: which is easier to implement in the evaluator?
- GPU: can Option B run a second model on the same GPU?

**Deliverable:** Phase W report — watchdog design decision (A, B, or hybrid), with metrics from synthetic testing. No Gazebo runs. No implementation yet.

## 9. Gaps our work fills (novelty)

- **Tick-level LLM soccer coaching:** No prior work (LLCoach is play-level, seconds-to-minutes).

- **Behavioral probing of a 3B model's soccer vocabulary:** No prior work.
- **Text-only LLM evaluation for robot soccer:** No prior work (everyone uses sim runs). Our ~85× speedup enables rapid iteration.
- **Cross-model inter-lingua validation:** Testing the same controlled vocabulary across Qwen2.5-3B and Llama-3.2-3B to determine model-agnostic vs model-specific vocabulary.
