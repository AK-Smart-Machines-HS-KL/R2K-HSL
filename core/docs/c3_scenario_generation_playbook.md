# C3 Scenario Generation Playbook

> **Purpose.** Handover of the C3 Phase 1 walkthrough decisions (2026-08-01):
> how a scenario package (`scenario.json` + `analysis.md` with Expert/Oracle)
> must be written so that `qwen2.5:3b` actually executes it. Captures the
> probe-verified vocabulary rules, the human soccer-reasoning patterns fed in
> during the TC-01..05 walkthrough, and the validation loop used to check a
> generated package.
>
> **Model-agnostic.** This document is a plain spec. It can be read by a human,
> and it can be fed verbatim (as context/system prompt) to a full-fledged LLM
> to generate new scenario packages consistently. It does not depend on a
> specific generation model, Ollama, or a hosted API.
>
> **Reading order.** A generating agent should read §1-§10 (the rules) once,
> then §11 (exemplars) to copy the shape, then §10 (validation) before
> delivering a package.

---

## 1. Usage

- **As a human spec:** the reference for Phase 2 (rework all `analysis.md`
  files) and for authoring new scenarios by hand.
- **As an LLM prompt:** paste §1-§11 as context, then ask the model to produce
  a new scenario package. Provide the target `tactical_situation`; the model
  returns `scenario.json` + `analysis.md`. Always run §10 validation after.
- **Companion files:** `c3_vocabulary_dictionary.md` (full probe evidence per
  vocabulary entry), `c3_testcase_review.md` (P0-P3 test-case findings),
  `src/results/vocab_probe_log.md` (raw probe logs).

| Item | Value | Source |
|---|---|---|
| Field size | 9 m × 6 m | `referee_rulebook.md` |
| X range | [-4.5, +4.5] (own goal at -4.5, opponent goal at +4.5) | `rules_core.txt` |
| Y range | [-3.0, +3.0] | `rules_core.txt` |
| Attack direction | always toward +X (red goal) | `rules_core.txt` |
| Goal mouth | |Y| ≤ 0.9 at X = ±4.5 | `referee_rulebook.md:99` |
| Goal area | corners (±3.5, ±1.0) in front of each goal | `referee_node.py:59-60` |
| Corner flags | (±4.5, ±3.0) | `referee_node.py:482-486` |
| Kick-in placement | sideline at exit point (±3.0, ±3.0) | `referee_node.py` |
| Goal-kick placement | nearer corner of goal area: (±3.5, ±1.0) | `referee_node.py:476-480` |
| Center | (0, 0) | — |

**Rules of the game (code facts, not RoboCup standards):**
- **No offside rule exists** in `referee_node.py`. A through ball behind the
  line is never called back.
- **No throw-in.** Bots have no hands; the sideline restart is a **kick-in**.
- **Restart mechanics are referee-owned** — the LLM must never produce them;
  it only receives passive awareness via `match_state.status`.
- **Role-aware kick:** non-goalie bots aim kicks at the opponent goal (+X). A
  "clear to the sideline" is not executable.
- **Goalie blending override:** the bridge pulls the goalie toward the goal
  line when the ball is near; a "sweeper goalie at X=-3.0" is not enforceable.

## 3. Scenario package structure

A scenario package lives at `src/scenario/<name>/` with four files:

```
scenario/<name>/
  scenario.json       # entity positions (v6 schema)
  analysis.md         # Expert + Oracle (this playbook §4)
  field_diagram.png   # generated by tools/gen_field_diagrams.py
  kpi_targets.json    # per-scenario KPI thresholds (regression suite)
```

**`scenario.json` — v6 schema:**

```json
{
  "scenario_name": "3vs3_<tactic>",
  "mode": "3vs3",
  "tactical_situation": "Short description of the tactical test situation",
  "entities": {
    "soccer_ball": {"x": 0.0, "y": 0.0},
    "blue_1": {"x": 0.0, "y": 0.0},
    "blue_2": {"x": 0.0, "y": 0.0},
    "blue_3": {"x": 0.0, "y": 0.0},
    "red_1": {"x": 0.0, "y": 0.0},
    "red_2": {"x": 0.0, "y": 0.0},
    "red_3": {"x": 0.0, "y": 0.0}
  }
}
```

- `scenario_name` MUST match the filename (without `.json`).
- `mode` selects the prompt fragments (`rules_<mode>.txt` + `samples_<mode>.txt`).
- Entity names are flat: `blue_1`, `blue_2`, `blue_3`; never namespaced.
- All positions must lie inside the field (§2) unless the kick-in exception
  applies (restart bot MAY go up to 1 m outside).

**`analysis.md` — section order is FIXED:**

```
# 3vs3_<tactic> — Analysis

## Expert (technical)     <- first, see §4

<game-state analysis>

## Oracle (strategic)     <- second, see §4

<recommended actions>
```

## 4. Section semantics (the core correction)

The two sections have **different jobs** and must never be swapped or merged:

| | **Expert (technical)** | **Oracle (strategic)** |
|---|---|---|
| Job | **Analyse the game state** | **Things recommended to do** |
| Content | Facts: positions, geometry, angles, reachability, numbers | Commands: per-blue-bot actions with explicit targets |
| Imperatives | NONE — no "should", no commands, no recommendations | Every blue bot gets a concrete instruction |
| Coordinates | All referenced entities get X,Y | **Every positional verb carries explicit X,Y** |
| Example | "The ball is at (3.0,2.0)... shooting angle is too narrow" | "blue_1 moves to (X=-1.8, Y=-0.4)" |

**Evidence (probe series G, `vocab_probe_log.md`):**
- **G1 == G2:** when the oracle carries explicit coordinates, adding the expert
  text changes nothing (model copies the coordinates). Expert is redundant when
  oracle has coords.
- **G3:** with expert only (no oracle), the model *reasons* from the analysis —
  it noticed "blue_3 too far from goal area" and moved blue_3 toward the goal
  (emergent correction) — but produced fuzzy, imprecise coordinates.
- **Conclusion:** expert drives *emergent tactical corrections*; oracle drives
  *coordinate precision*. The hybrid (expert context + oracle-with-coords) gives
  both.

**Why coordinates are mandatory (probe E/F):**
- E1 (oracle without coords): "blue_2 takes the fastest way into the open space
  on the left wing" → model placed blue_2 **on the ball**. "seeks a kicking
  position" → model moved blue_1 to the goal line. Degenerate positioning.
- E2 (oracle with coords): all three targets copied correctly.
- F1 (short desc, no coords): "blue_3 stays back as the deep backup" → model
  moved blue_3 **forward** (inverted the negation).
- F2 (short desc, with coords): all three targets copied correctly.

**Rule: every positional/negational verb ("move to", "stays back", "holds",
"positions at", "ready at") gets a coordinate. If a verb has no coordinate, the
3B model will guess — and guess wrong.**

## 5. Distilled soccer reasoning patterns (human knowledge)

These are the reasoning patterns a human expert applies when reading a world
state and prescribing actions. A generating LLM should apply them in the
Expert (analysis) and Oracle (action) sections. Each entry: pattern, what to
check, how to express it, source scenario.

### P1 — Reachability & free time
- **Check:** distance from ball-carrier to nearest opponent.
- **Express (Expert):** "distance from blue_1 to red_1 is large enough that
  blue_1 has free time to maneuver — red_1 cannot reach the ball quickly."
- **Express (Oracle):** use the free time: take a deliberate action instead of
  rushing.
- **Source:** TC-04 (fast_counter).

### P2 — Out of reach = ignorable
- **Check:** opponents far upfield/side that cannot influence the ball within
  a few seconds.
- **Express (Expert):** "red_2 and red_3 stand far upfield and can be ignored —
  they are out of reach."
- **Source:** TC-04 (fast_counter), TC-02 (attack_wing: "red_3... cannot
  defend this wing action").

### P3 — Shooting angle
- **Check:** is there a straight lane from the ball-carrier to the goal mouth
  (|Y|≤0.9 at X=4.5)?
- **Express (Expert):** "The shooting angle toward the goal mouth is too
  narrow — blue_1 cannot shoot directly; the ball sits between blue_1 and the
  goal. Blue_1 must move around the ball to gain a usable angle."
- **Express (Oracle):** "blue_1 moves around the ball to open a shooting
  angle."
- **Source:** TC-02 (attack_wing).

### P4 — Numbers advantage
- **Check:** count blue vs red bots near the ball and in the contested zone.
- **Express (Expert):** "Two blue bots are near the ball; no red bot is within
  2 m of the ball. Blue has a numbers advantage in the center."
- **Source:** TC-01 (attack_center).

### P5 — Anticipate the block (act before the opponent responds)
- **Check:** which opponent will move to block the ball-carrier, and where the
  free receiving space will be.
- **Express (Oracle):** "Red_2 will try to block blue_1, so blue_2 must
  actively move into the receiving position — blue_2 cannot wait." 
- **Source:** TC-02 (attack_wing).

### P6 — Pass into space (receiver must be positioned first)
- **Check:** is the intended receiver already in the space the pass will be
  played into?
- **Express (Expert):** "blue_2 is too far back to receive a pass played into
  the space behind red's defense."
- **Express (Oracle):** "By the time blue_1 can pass, blue_2 should be
  positioned in red's half... ready to receive."
- **Source:** TC-02 (attack_wing).

### P7 — Rebound readiness
- **Check:** after a shot, where will the ball bounce back?
- **Express (Oracle):** "blue_3 moves slightly forward and stays ready to
  receive the ball if the shot bounces back."
- **Source:** TC-01 (attack_center).

### P8 — Counter-attack cover
- **Check:** if possession is lost, is the deepest bot/goalie positioned to
  intercept early?
- **Express (Oracle):** "blue_1 moves to the middle of its own half (X=-2.25),
  ready to intercept the ball early if red starts a counter attack." / "blue_3
  stays back as the deep cover at (X=-4.0, Y=0.0)... while blue_1 and blue_2
  push forward."
- **Source:** TC-01 (attack_center), TC-04 (fast_counter).

### P9 — Lane / dribble denial
- **Check:** where will the opponent's next dribble/pass go? Place a bot to
  cut it off.
- **Express (Oracle):** "blue_2 moves down into the center lane to cut off
  red_1's dribbling path toward the goal."
- **Source:** TC-03 (defensive_crisis).

### P10 — Press escape
- **Check:** is the ball-carrier under pressure? Is there a safe passing
  outlet?
- **Express (Oracle):** "blue_1 keeps the ball under pressure and passes to a
  teammate instead of forcing forward. blue_2 moves to the center line at
  (0.0, 0.8) as a backup passing option."
- **Source:** TC-05 (pressing_trap).

## 6. Vocabulary constraints

Only these verbs and nouns are guaranteed to be understood correctly by
`qwen2.5:3b` (full evidence: `c3_vocabulary_dictionary.md`).

### 6.1 Usable verbs
`move to X,Y`, `receive pass from X`, `support run to X,Y`, `hold position`,
`mark X` (stay close to a specific player), `cover a zone / cover position`
(position in an area to block shots/passes), `clear the ball`, `cover the
goal line`, `pass`, `shoot`, `cross`, `kick`.

### 6.2 Borderline (usable only with care)
- `press the ball` — needs robot-safe phrasing; drop the human "use your
  hands" twist.
- `chase the ball` — pair with a target: "chase the ball at X,Y".
- `cut inside` — human dribbling concept; not executable. Reject unless a
  movement paraphrase.

### 6.3 Reject
- `throw-in` — **does not exist** (no hands). RoboCup term: **kick-in**.
- `free-kick` / `direct free-kick` — wrong terminology for our restarts.
- `dive` (goalie) — human move, impossible for bots. Use "between ball and
  goal" instead.
- `penalty area` — we have a goal area, not a box. Use **goal area** with
  coordinates.
- `sweeper` — conflicts with the goalie-blending override.

### 6.4 Zone nouns need explicit bounds
- `own half` — only with bound: "own half = X from -4.5 to 0".
- `opponent half` — **broken** (model treats field as 0..9). Prefer "the red
  side of the center line".
- `goal area` — model hallucinates off-field coordinates. **Always give
  explicit coordinates**, never the noun alone.
- `center of the field`, `wing / flank / sideline`, `passing lane`,
  `formation`, `goal / goal line` — usable.

### 6.5 Roles
- Only **goalie / attacker / defender** are valid. `striker`, `supporter`,
  `midfielder`, `passer`, `receiver` are dead vocabulary (role condensation,
  2026-07-28).
- **Never define roles dynamically** ("the attacker is the bot closest to the
  ball") — the model rejects this and falls back to static soccer semantics
  with hedging (probe C2_striker_rule). Prefer situation-triggered position
  verbs: "blue_2 move to the ball", "blue_1 hold the goal line".
- If roles must appear, use them as labels of a previous assignment, never as
  derived concepts.

## 7. Referee-owned concepts (passive awareness only)

| Restart | Correct term | Placement (referee) |
|---|---|---|
| Ball over sideline | **kick-in** (never "throw-in") | sideline at exit point (±3.0, ±3.0) |
| Attacker over defender's goal line | **goal-kick** | nearer corner of goal area (±3.5, ±1.0) |
| Defender over own goal line | **corner kick-in** | corner flag (±4.3, ±2.8) |
| After a goal | **kickoff** | center (0,0), conceding team |

**The LLM never produces these mechanics.** It only needs passive awareness:
when `match_state.status` is `ball_out` / `goal_kick` / `corner_kick_in` /
`kickoff`, the restart bot may approach the ball up to 1 m outside the field.
All enforcement, freeze, and placement is referee-owned
(`referee_node.py`, `referee_rulebook.md`).

---

## 8. Forbidden content in model-facing text

The following NEVER appear in `analysis.md` (or any fragment fed to the LLM):

1. **KPI / benchmark names:** `shots_on_goal`, `shots_on_target`,
   `pass_completion_pct`, `restart_recovery_time_s`, `goalie_tactical_pct`,
   `composite`, `cluster_pct`, `oob_pct`, `role_diversity`, `possession`,
   `latency`.
2. **LLM-routing / implementation language:** "assign", "role switch",
   "Move targets", "route one bot wide", "the LLM should...".
3. **Bridge/execution internals:** "goalie blending", "tactical weight",
   "PD controller", "watchdog", "bridge".
4. **Universal-knowledge axioms** (e.g. "whoever controls the center controls
   the game", "wing play stretches the defense") — these belong in a separate
   soccer-universal-knowledge module, not in per-scenario text. Repeating them
   in every file creates contradiction potential.
5. **Offside, offside trap, fancy-pass penalties** — none exist in
   `referee_node.py`.

Boundary phrasing: use "Keep all blue bots inside the field boundaries"
(rules already forbid out-of-range Move targets; scenario text need not
repeat mechanics).

## 9. Anti-patterns (probe-verified failures)

| # | Anti-pattern | Symptom (probe) | Cause | Rule |
|---|---|---|---|---|
| A1 | Positional verb without coordinate | E1: "open space on left wing" → model put bot ON the ball | Model guesses, defaults to ball/goal | Every positional verb gets X,Y (§4) |
| A2 | Negation verbs ("stays back", "do not") | F1: "stays back as deep backup" → bot moved FORWARD | Model inverts negation | State the positive target with coords: "stays back at (X, Y)" |
| A3 | Dynamic role definition | C2: "striker = bot closest to ball" → hedged refusal | Role concept carries static soccer semantics | Position verbs, never derived roles (§6.5) |
| A4 | Zone noun without bounds | D5: "goal area" → off-field coords | Model hallucinates geometry | Concrete coordinates only (§6.4) |
| A5 | External concepts (KPIs, "assign") | — | Prompt teaches dead vocabulary | Never in model-facing text (§8) |

## 10. Validation protocol

Run this on every generated/edited package before committing.

1. **World ↔ diagram congruence.** Regenerate the diagram and compare
   byte-identical:
   ```bash
   cd src
   python3 tools/gen_field_diagrams.py --scenario 3vs3_<tactic> --output-dir /tmp/check
   cmp scenario/3vs3_<tactic>/field_diagram.png /tmp/check/3vs3_<tactic>_field_diagram.png
   ```
   (`cmp` equal = scenario.json is what the picture shows. The assistant
   cannot view PNGs; this is the verification method.)

2. **Coordinate grep.** Every positional/negational verb in the Oracle carries
   an explicit `(X=..., Y=...)`. Manual read or regex scan for verbs without a
   nearby coordinate.

3. **Cross-TC consistency.** No instruction contradicts another package (e.g.
   "play back to the goalie" when no bot starts near the goal). No KPI/LLM
   vocabulary (§8) leaked in.

4. **3B probe (behavioral check).** The decisive test — does qwen2.5:3b
   actually execute the oracle? Query format:
   - **System:** `You are a soccer analyst. Given a world state and a tactical
     instruction, output target X,Y positions for each blue bot. Format:
     blue_1: (X, Y), blue_2: (X, Y), blue_3: (X, Y). Output only the three
     lines.`
   - **Prompt:** `World state: <scenario.json entities verbatim>` + `Tactical
     instruction: <Oracle section>` + `Output the three target positions.`
   - **Ollama:** model `qwen2.5:3b`, temperature 0.0, num_predict 600,
     keep_alive 1h, stream false. (Use `tools/vocab_probe.py --series XX` to
     log the probe.)
   - **Judge:** do the returned positions match the oracle intent? Failure
     modes: bot placed on the ball, bot moved opposite to "stays back",
     fuzzy midpoints where a precise target was intended. → add coordinates
     and re-probe.

**`analysis.md`:**

```
# 3vs3_attack_center — Analysis

## Expert (technical)

The ball is at X=2.2, inside red's half, close to the center line. Two blue
bots are near the ball: blue_2 at (1.5, 1.2) and blue_3 at (1.5, -1.2). The
red defense is stretched: both red defenders stand wide on the wings (red_2 at
(2.8, 2.2), red_3 at (2.8, -2.2)), so the middle of the field is open. The red
goalie is off-center at (4.2, 0.5), leaving the far side of the goal exposed.
No red bot is within 2 m of the ball. Blue has a numbers advantage in the
center.

Blue_2 moves to the ball and kicks toward the red goal, aiming at the open
side of the goal (away from the red goalie at Y=0.5). Blue_3 moves slightly
forward and stays ready to receive the ball if the shot bounces back. Blue_1
moves to the middle of its own half (X=-2.25), ready to intercept the ball
early if red starts a counter attack. Keep all blue bots inside the field
boundaries.
```

Patterns applied: P4 (numbers), P7 (rebound), P8 (counter cover).

## 12. Extension notes

- **Free-form scenarios.** The TC-style is `3vs3_<tactic>` packages in the v6
  matrix. For other modes/sizes, the same rules apply: mode prefix must match
  existing fragments (`rules_<mode>.txt` + `samples_<mode>.txt`), and every
  package keeps the 4-file structure. `2vs2_default` shows the 2-bot variant
  (goalie + attacker split, "one bot falls back to goalie position").
- **Adding exemplars.** Whenever a TC passes validation, append it to §11 so
  the exemplar set always reflects the current best practice. The four above
  are the template.
- **New vocabulary entries.** Anything beyond §6 must be probed
  (`tools/vocab_probe.py`, logged to `results/vocab_probe_log.md`) before use
  — the dictionary is evidence-based, never assumed.
- **Future automation.** A `tools/gen_scenario.py` (full-LLM-driven, fed this
  playbook) plus auto-validation (§10) is the planned evolution; not built yet.
